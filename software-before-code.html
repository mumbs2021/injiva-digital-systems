Before the first line of code: define what success means

A practical brief for turning an unclear software request into testable requirements.

By INJIVA Digital Systems • 30 October 2026 • Practical guide

IN THIS FIELDNOTE

← All insights
01

Start with a real task

Describe who needs to do what, what blocks them today and how often it happens. “We need a portal” is a solution idea. “Staff need to check a request without calling three departments” describes a problem that can be investigated. Interview the people doing the work and observe the exceptions, not only the ideal sequence.

02

Write acceptance examples

Define observable outcomes before estimating the build. For a request workflow, specify who may submit, who may approve and what happens when information is missing. A useful acceptance example might be: an incomplete request stays editable, displays a clear explanation and cannot proceed to approval. Include permissions, validation, failure handling and accessible interaction in the conversation.

03

Design the whole journey

Map entry, completion and recovery. What happens if a connection fails, a user makes a mistake or a record already exists? Use semantic controls, visible labels and keyboard-friendly interactions. W3C’s accessibility tutorials provide practical guidance on forms, navigation and page structure; consult them while designing, rather than treating accessibility as a final visual check.

04

Make handover part of the scope

Agree ownership of the source code, environments, documentation and ongoing support before implementation. Identify who will manage access, approve releases and respond to failures. A launch plan should include a way to verify the release and restore a known working state if the change fails.

05

Take this into your next meeting

Prepare a one-page brief with the user task, current friction, desired outcome, important constraints and three acceptance examples. Add the decisions that remain open. This creates a useful starting point for discovery without pretending that every requirement is already known.
